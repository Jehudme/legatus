# Living Documentation & Drift Prevention Specification

## Document Metadata
* **Guideline ID:** GL-0010
* **Scope:** Universal Documentation (`docs/`)
* **Status:** Final Implementation Standard
* **Audience:** Core Systems Engineers, Platform Contributors, Documentation Stewards
* **Normative Conformance:** RFC 2119 / RFC 8174 (`MUST`, `MUST NOT`, `REQUIRED`, `SHALL`, `SHALL NOT`, `SHOULD`, `SHOULD NOT`, `RECOMMENDED`, `MAY`, `OPTIONAL`)

---

## 1. Executive Summary & Purpose

Documentation rot is a critical reliability hazard in distributed systems. When documentation diverges from source code, operators execute incorrect troubleshooting procedures, security engineers evaluate outdated threat models, and software engineers build against non-existent contracts. In the Legatus ecosystem, where high-performance C++20 daemons (`legatusd`) interface with Java 21 orchestration servers and Solix guest runtimes, unverified or obsolete documentation directly produces deployment failures and cluster downtime.

This specification establishes the **Living Documentation Invariant** and the **Zero-Drift Mandate**. Documentation is defined as a first-class engineering artifact possessing the same rigor, versioning, review process, and automated verification as executable code. This standard defines non-negotiable rules for synchronizing code and documentation, verifying code snippets against compilers, auditing CLI/API parameter truth, and methodically pruning dead knowledge.

---

## 2. Normative Invariants & Core Principles

All contributors and documentation authors **MUST** adhere to the following binding rules:

1. **The Zero-Drift Mandate:** Code and documentation **MUST** be authored, updated, and committed within the exact same Git commit or pull request. A pull request that changes code without updating corresponding guides, specifications, or CLI help strings **SHALL NOT** be approved or merged.
2. **Compiler-Verified Snippets Invariant:** Every code snippet, compilation example, or configuration snippet presented in documentation **MUST** be directly validated against automated build targets or test suites. Hand-typed, uncompiled code snippets in documentation are strictly prohibited.
3. **CLI Flag Synchronicity:** Every documented CLI command, flag, environment variable, and default value for `legatus`, `legatusd`, or `legatus-runner` **MUST** match the actual `CLI11` option bindings in source code byte-for-byte.
4. **API and DTO Precision:** Every documented HTTP REST endpoint, query parameter, and JSON payload schema **MUST** match the Jackson annotations, Spring DTO records, and OpenAPI schemas generated by `legatus-server`.
5. **No Speculative or Unreleased Features:** Documentation **MUST NOT** document future, planned, or unmerged features in existing production guides. Features under development **MUST** be isolated in branches or explicitly marked with a prominent `> [!WARNING] Experimental / Unreleased` banner.
6. **Methodical Archival of Dead Knowledge:** Obsolete documentation, superseded protocols, and abandoned RFCs **MUST NOT** remain in active documentation directories. Superseded documents **MUST** be moved to `docs/archive/` with a top-level notice linking to the current authoritative document.

## 3. Structural Specification & Schema

### 3.1 Documentation Directory Taxonomy

The `docs/` tree is strictly partitioned to prevent scope confusion:

```text
docs/
├── architecture/       # High-level component topology, sequence diagrams, wireframes
│   ├── sequences/      # UML sequence diagrams (Mermaid / SVG)
│   └── wireframes/     # UI/Cockpit visual layouts and mockups
├── dev/                # Developer specifications and internal engineering standards
│   ├── decisions/      # Architecture Decision Records (ADRs, MADR format)
│   ├── guidelines/     # The Engineering Guidelines Suite (GL-0000 - GL-0011)
│   └── milestones/     # Phased delivery plans, blocker tracking, and DoD
├── guides/             # End-user, operator, and developer operational guides
├── specs/              # Subsystem specifications (contracts, wire frames, state machines)
│   └── protocols/      # Layer 7 network protocols (LCTP, WebSocket, REST)
└── archive/            # Historical, deprecated, or superseded specifications
```

### 3.2 Document Verification Annotations

When embedding code snippets or configuration files in Markdown, authors **MUST** use explicit fenced code blocks with language identifiers. Where snippets correspond to source files, authors **MUST** reference the source file and line range using Markdown links:

```markdown
```cpp

When archiving a superseded document to `docs/archive/`, the file **MUST** be prepended with the following canonical deprecation alert:

## 5. Concrete Production Example

### Verifying CLI Flags Against Source Code Invariants

Below is an operational specification excerpt for the `legatus` CLI `drain` command in `docs/guides/05-worker.md`:

```markdown
### Worker Drain Command

The `drain` subcommand signals `legatusd` via local `nng` IPC to transition the node into `DRAINING` state, refusing new task dispatches while allowing active guest runners to terminate gracefully within the specified deadline.

#### Syntax & Options

```bash
legatus drain [--timeout-seconds <sec>] [--force]
```

| Flag | Type | Default | CLI11 Source Reference | Behavior |
| :--- | :--- | :--- | :--- | :--- |
| `--timeout-seconds, -t` | `uint32` | `300` | `worker/cli/commands/drain.cpp#L24` | Maximum seconds to await active tasks before SIGKILL escalation. |
| `--force, -f` | `bool` | `false` | `worker/cli/commands/drain.cpp#L28` | Skip waiting for active tasks; abort running tasks immediately. |
| `--reason, -r` | `string` | `"Manual drain"` | `worker/cli/commands/drain.cpp#L32` | Audit message forwarded to `server` in `DRAIN_NOTICE` frame. |
```

#### Automated Verification Script (`scripts/verify-cli-docs.sh`)
```bash
#!/usr/bin/env bash
set -euo pipefail

# Ensure every documented flag in docs/guides/05-worker.md exists in worker/cli/commands/drain.cpp
for flag in "--timeout-seconds" "--force" "--reason"; do
  if ! grep -q "$flag" worker/cli/commands/drain.cpp; then
    echo "ERROR: Documented flag $flag not found in drain.cpp source!" >&2
    exit 1
  fi
done
echo "CLI documentation verified against CLI11 source bindings."
```

## 6. Anti-Patterns & Counter-Examples (What NOT to Do)

### Anti-Pattern 1: The "I'll Document It in a Later PR" Fallacy
* **Flawed Practice:** An engineer merges a PR adding an `--instruction-quota` flag to `legatus-runner` without updating documentation, stating: "I'll submit a docs PR next sprint."
* **Failure Mode:** The docs PR is forgotten. Operators deploy the new binary without knowing the flag exists. Cluster operators experience unmetered runaway tasks because the default behavior changed without documented operator guidance.
* **Corrected Approach:** Reject the PR immediately at review time. Code, unit tests, and documentation updates **MUST** be co-committed in the same PR.

### Anti-Pattern 2: Documenting Unreleased Aspirational Features
* **Flawed Practice:** Writing in `docs/guides/02-server.md`: "Legatus supports distributed multi-region Raft consensus clustering" when only single-node H2 persistence is implemented.
* **Failure Mode:** Users build deployment pipelines expecting Raft endpoints, only to discover connection crashes. Engineering credibility is destroyed.
* **Corrected Approach:** Only document features verified by automated tests in `master`. For roadmap features, refer to `docs/dev/milestones/`.

### Anti-Pattern 3: Ghost Documentation & Stale Files
* **Flawed Practice:** When migrating from REST polling to WebSocket LCTP, leaving `docs/specs/protocols/worker-polling.md` in place with no deprecation notice.
* **Failure Mode:** New contributors read the old spec and implement polling logic in client libraries, introducing conflicting communication models.
* **Corrected Approach:** Move the file to `docs/archive/protocols/worker-polling.md`, add the canonical Deprecation Warning banner, and update the index.

## 7. Verification & Compliance Checklist

Reviewers and documentation maintainers **MUST** enforce the following checklist on every PR modifying or adding documentation:

- [ ] **Co-Commit Compliance:** All code changes altering CLI options, wire schemas, or configuration keys are accompanied by documentation changes in the same PR.
- [ ] **Compiler Verification:** All code and configuration snippets have been verified against active build targets or CI tests.
- [ ] **CLI11 Match:** CLI options, short flags, data types, and default values match source code bindings exactly.
- [ ] **DTO Match:** Server JSON payload structures match Spring Boot Jackson DTO definitions.
- [ ] **No Speculative Claims:** Unreleased or planned features are strictly excluded from operational guides.
- [ ] **Link Integrity:** All internal relative Markdown links point to valid, existing repository paths.
- [ ] **Pruning & Archival:** Deprecated documents are moved to `docs/archive/` with the mandatory `[!CAUTION]` header.
